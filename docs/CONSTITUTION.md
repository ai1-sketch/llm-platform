# الدستور الهندسي للمشروع (Engineering Constitution)

> الوثيقة الحاكمة العليا لمنصّة الـ LLM الداخلية. كل قرار، PR، أو إضافة قاعدة يُقاس عليها. عند التعارض، يسبق هذا الدستور أي وثيقة أخرى — بما فيها [CLAUDE.md](../CLAUDE.md) (عقد المساعد التابع له).

> **الحالة:** نافذة v1 (مُعتمدة ومُلزِمة) · **النطاق:** كل أعضاء الفريق والمساعدين (assistants) · **يُقرأ مع:** [ARCHITECTURE_RULES](ARCHITECTURE_RULES.md) · [ERROR_AND_OBSERVABILITY_POLICY](ERROR_AND_OBSERVABILITY_POLICY.md) · [DECISIONS](DECISIONS.md) · [PROGRESS_MAP](PROGRESS_MAP.md)

## 1. الدور والمعيار

نعمل تحت قيادة **Chief Software Architect** بخبرة أنظمة موزّعة ضخمة. المعيار غير قابل للتفاوض: كود وحوكمة **Clean / Scalable / Maintainable**.

- **المعمارية:** Clean Architecture — طبقات مفصولة بعقود، التبعيات تتّجه نحو الداخل، التفاصيل (محرّك، مزوّد، سحابة) قابلة للاستبدال.
- **القاعدة الذهبية:** **نظيف ≠ معقّد.** النظافة تعني الوضوح وقلّة المفاجآت وقابلية الاستبدال — لا كثرة الطبقات والميزات. التعقيد بلا مبرّر هو *عيب*، لا إنجاز.
- **المبدأ المركزي للمنصّة:** "نفس الشكل، صناديق أكبر" — العقد ثابت (OpenAI-compatible API)، والتوسّع تكبيرُ صناديق خلفه لا إعادة بناء. هذا ينطبق على وثائق الحوكمة نفسها: نقسّمها لاحقاً عند وجود كود يستحق الانفصال، لا قبله.

## 2. القوانين الجوهرية (Core Laws)

قواعد معرّفة، كل واحدة قابلة للتحقّق بشرياً أو بـ linter.

| المعرّف | القاعدة | الفحص |
|---|---|---|
| **R-LAW-01** | **الجودة أولاً، لا اختصارات.** لا يُدمج كود معطوب أو "مؤقّت سنصلحه لاحقاً" دون تذكرة دَيْن تقني موثّقة في [DECISIONS](DECISIONS.md). | لا `TODO`/`FIXME` بلا رابط تذكرة ADR |
| **R-LAW-02** | **البساطة / YAGNI ومنع الهندسة المفرطة.** لا تُبنى قدرة قبل وجود حاجة حقيقية لها الآن، وأي تجريد/طبقة/أداة جديدة تتطلّب مبرّراً مكتوباً يربطها بحاجة قائمة. نُفضّل القرارات القابلة للعكس؛ والقرار أحادي الاتجاه (one-way door) يُعالَج عبر حارس §5. | يجتاز "حارس التضخيم" §5، والنتيجة مسجّلة في ADR |
| **R-LAW-03** | **Config-driven (12-Factor).** كل ما يتغيّر بين البيئات (عناوين، مفاتيح، أسماء موديلات، حدود) خارج الكود في `config`/`env`. لا قيم hardcoded ولا أسرار في git. | فحوص R-ARCH-02/20: `git ls-files \| grep -E '(^models/\|\.env$)'` فارغ، ولا مطابقة لـ `sk-` في ملف متتبَّع |
| **R-LAW-04** | **الفصل بين الطبقات.** الواجهة → البوّابة → المحرّك → الموديل؛ كل طبقة تعرف جارتها عبر عقد `/v1` فقط، وتُستبدَل دون مساس بالأخريات. | لا طبقة تتجاوز جارتها مباشرةً (R-ARCH-10/11/12) |
| **R-LAW-05** | **العقد الموحّد إلزامي.** كل تخاطب عبر OpenAI-compatible API. لا عميل يربط نفسه بخصوصيات محرّك بعينه ولا يتجاوز البوّابة. | `api_base`/`base_url` لأي عميل = منفذ البوّابة فقط (R-ARCH-13) |
| **R-LAW-06** | **الأمان مبنيّ لا مُلصق.** أساسيات الأمان الرخيصة تُطبَّق الآن (منفذ بوّابة غير مكشوف، مفاتيح افتراضية، أسرار خارج الكود)؛ الثقيل يُؤجَّل بوسم صريح في [DECISIONS](DECISIONS.md). | منفذ البوّابة بلا `ports:` عام (R-ARCH-24)، وراجع [ERROR_AND_OBSERVABILITY_POLICY](ERROR_AND_OBSERVABILITY_POLICY.md) |

التفاصيل المعمارية الملزمة في [ARCHITECTURE_RULES](ARCHITECTURE_RULES.md)؛ سياسة الأخطاء والرصد في [ERROR_AND_OBSERVABILITY_POLICY](ERROR_AND_OBSERVABILITY_POLICY.md).

## 3. معيار "تمّ" (Definition of Done)

لا يُعتبر أي تغيير ذي قيمة مكتملاً إلا باستيفاء كل البنود — وكلّها قابلة للفحص الثنائي (نعم/لا):

- [ ] **يحقّق هدفاً معرّفاً** مرتبطاً ببند `P-NN` في [PROGRESS_MAP](PROGRESS_MAP.md).
- [ ] **لا يكسر العقد** (`/v1`) ولا يكشف طبقة على أخرى (R-LAW-04/05).
- [ ] **الإعداد خارجي** ولا أسرار في الكود/الـ image/سجلّ git (R-LAW-03).
- [ ] **قابل للتشغيل بـ** `docker compose up` دون خطوات يدوية خفيّة.
- [ ] **رصد:** كل تغيير يُضيف مسار طلب (request path) جديداً يُصدر `request_id` + سجلّ كلفة وفق [ERROR_AND_OBSERVABILITY_POLICY](ERROR_AND_OBSERVABILITY_POLICY.md). (تغيير لا يضيف مساراً معفى.)
- [ ] **موثّق:** أي قرار جوهري مُسجَّل كـ ADR في [DECISIONS](DECISIONS.md)، وأي إضافة قاعدة/أداة/طبقة دُوّن فيها حُكم حارس §5.
- [ ] **مُراجَع** عبر بوّابات §4 المنطبقة، بلا اعتراض مفتوح.

## 4. آلية العمل متعدّدة المساعدين (Multi-Assistant Workflow)

كل تغيير ذي قيمة يمرّ بدورة: **مسوّدة من المعماري ← مراجعة الخبراء المعنيّين ← قبول.**

1. **المسوّدة (Draft):** المعماري (أو من ينوب عنه) يكتب التغيير/القاعدة مع تبريرها وربطها بحاجة قائمة وببند `P-NN`.
2. **المراجعة (Review):** تُطبَّق البوّابة المنطبقة فقط (لا كلّها في كل مرة — تجنّباً للتضخيم).
3. **القبول (Accept):** بعد إغلاق كل اعتراض. أي اعتراض غير مُغلَق = حجب.

### بوّابات المراجعة (Review Gates)

الفريق فعلياً = مالك واحد + مساعدو AI؛ لذا **"القبّعتان" أدناه قبّعات يلبسها المراجِع نفسه، لا أشخاص منفصلون.** أدوار التشغيل المتقدّمة (SRE/HA) مؤجَّلة حتى يوجد تشغيل إنتاجي فعلي.

| القبّعة | تُلبَس متى | تفحص |
|---|---|---|
| **مراجعة معمارية / أمان** | تغيير بنيوي، تبعية جديدة، مصادقة/مفاتيح/منافذ/أسرار/شبكة | فصل الطبقات واتجاه التبعيات والعقد الموحّد (R-LAW-04/05)، حارس §5، R-LAW-06 وعدم كشف البوّابة أو تسريب PII |
| **مراجعة تشغيل / جودة** | Docker/Compose/CI/الإعداد، ومنطق البوّابة/المحرّك، وأي تغيير ذي قيمة | R-LAW-03 وقابلية النقل وإعادة الإنتاج، صحّة العقد ومعالجة الأخطاء، ومعيار "تمّ" §3 وحالات الحافّة |

> القاعدة: تُطبَّق القبّعة المنطبقة فقط. تغيير صغير قد تكفيه قبّعة واحدة؛ تغيير بنيوي يحتاج كلتيهما. **لا تغيير ذو قيمة يُقبل بلا مراجعة واحدة على الأقل.**

## 5. حارس ضدّ التضخيم (Anti-Bloat Guard)

التعقيد دَيْن. **القاعدة الافتراضية: لا.** كل إضافة قاعدة/أداة/طبقة/تجريد يجب أن تجتاز كل الأسئلة التالية، وإلا تُرفض:

- [ ] **حاجة الآن؟** هل تحلّ مشكلة قائمة فعلاً (لا متخيَّلة/مستقبلية)؟
- [ ] **لا بديل أبسط؟** هل استُنفد كل حلّ موجود/أبسط قبل الإضافة؟
- [ ] **قابلة للتحقّق؟** هل يمكن لمراجِع أو linter فحصها؟ القاعدة التي لا تُفحَص ضوضاء.
- [ ] **لا تكرار؟** هل تتعارض مع/تكرّر قاعدة قائمة؟ (نُعدّل القائمة لا نُضيف).
- [ ] **كلفة العكس مقبولة؟** إن كان القرار أحادي الاتجاه، يُوسَم "قرار ثقيل" ويُراجَع بعناية.

**متى نرفض صراحةً:** قاعدة تنظّر لحالة لم تقع · أداة "قد نحتاجها" · طبقة تجريد بمستخدم واحد · ضابط enterprise (Kubernetes/SSO/HA/autoscaling) في مرحلة 1–10 مستخدمين · قاعدة لا يمكن فحصها.

> 💡 نقيس عدد القواعد كما نقيس الكود: الأقلّ الذي يكفي أفضل. حذف قاعدة فائضة عملٌ محمود مثل إضافة قاعدة ضرورية.
>
> **إلزامي:** حُكم هذا الحارس (قبول/رفض + المبرّر) يُكتب كحقل صريح في ADR ضمن [DECISIONS](DECISIONS.md) — وإلا يبقى R-LAW-02 رأياً غير قابل للفحص.
