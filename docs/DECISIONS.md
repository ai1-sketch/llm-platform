# DECISIONS — Architecture Decision Log (ADR)

سجلّ القرارات المعمارية لمنصّة LLM الداخلية. **قاعدة إلزامية:** كل قرار معماري (يؤثّر على الطبقات، العقود، أو الحدود بين المكوّنات) **يُسجَّل هنا كـ ADR**. لا قرار معماري شفهي.

## صيغة ADR المختصرة

| الحقل | الوصف |
|------|-------|
| **ID** | `ADR-NNN` تسلسلي، لا يُعاد استخدامه |
| **Title** | جملة واحدة تصف القرار |
| **Status** | `مقترح` \| `مقبول` \| `مرفوض` \| `مُلغى` \| `مُستبدَل بـ ADR-NNN` |
| **Context** | المشكلة/القوى الدافعة (لماذا نقرّر الآن) |
| **Decision** | ما تقرّر فعلاً (فعل صريح) |
| **Consequences** | النتائج والمقايضات (إيجابي/سلبي) |
| **Anti-Bloat (§5)** | حُكم حارس التضخّم لأي ADR يُضيف قاعدة/أداة/طبقة/تبعية: `مقبول`/`مرفوض` + سطر مبرّر (R-003). `N/A` لغير المُضيف. **إلزامي من ADR-026 فصاعداً.** |

**القواعد:**
- `R-ADR-01` — كل ADR **موجز وقابل للفحص**؛ ‏3-5 أسطر **إرشادي** للقرارات البسيطة، والقرارات الحاملة توسّع بقدر الحاجة لا أكثر (الحقول الإلزامية هي البوّابة).
- `R-ADR-02` — لا يُعدَّل **جسم** ADR مقبول (Context/Decision/Consequences)؛ القرار المعاكس = ADR جديد يستبدله. **يُسمح بتحديث حقل `Status` فقط** (مثل `مقبول → مُستبدَل بـ ADR-NNN` أو إضافة "مُنفَّذ") للإشارة لـ supersession/حالة التنفيذ — كما في ADR-006/016/022.
- `R-ADR-03` — أي PR يغيّر طبقة/عقد دون ADR مرجعي = يُرفض في المراجعة.

> **حقل Anti-Bloat (§5):** إلزامي لكل ADR **مُضيف** من **ADR-026 فصاعداً** (تجسيد R-003). الـ ADRs الأقدم المُضيفة (011/012/020…) تسبق هذا الحقل؛ مبرّرها §5 مذكور inline في Context/Consequences ولا يُعدَّل جسمها (R-ADR-02).

## ADR-001 — توحيد كل شيء خلف OpenAI-compatible API
**Status:** مقبول
**Context:** تعدّد محرّكات الاستدلال والموديلات يخلق تشظّياً في التكامل.
**Decision:** العقد الثابت بين كل الطبقات هو OpenAI-compatible API؛ أي مكوّن يلتزم به.
**Consequences:** (+) تبديل المحرّك/الموديل دون لمس الطبقات العليا. (−) قيود على ميزات خاصة بمحرّك معيّن خارج العقد.

## ADR-002 — LiteLLM كبوّابة مركزية إلزامية
**Status:** مقبول
**Context:** نحتاج نقطة واحدة للمفاتيح، التوجيه، تتبّع الكلفة، والحصص.
**Decision:** كل الطلبات تمرّ عبر LiteLLM gateway؛ لا اتصال مباشر بالمحرّكات/المزوّدين.
**Consequences:** (+) تحكّم وحوكمة مركزية وقابلية مراقبة. (−) نقطة فشل وحيدة تحتاج عناية تشغيلية لاحقاً.

## ADR-003 — Open WebUI كواجهة المستخدم
**Status:** مقبول
**Context:** نحتاج واجهة جاهزة تتكلّم OpenAI-API دون بناء frontend من الصفر.
**Decision:** اعتماد Open WebUI كطبقة واجهة، متّصلة حصراً بـ LiteLLM.
**Consequences:** (+) سرعة إطلاق وتجربة مستخدم ناضجة. (−) تخصيص محدود ضمن قدرات المشروع.

## ADR-004 — محرّك الاستدلال: llama.cpp الآن → vLLM لاحقاً
**Status:** مقبول — **مُنفَّذ بالكامل**: القفزة إلى vLLM تحقّقت محلياً ([ADR-028](DECISIONS.md))
**Context:** نحتاج تشغيلاً محلياً بسيطاً الآن مع مسار توسّع سحابي مستقبلاً.
**Decision:** llama.cpp محلياً حالياً، vLLM في السحابة لاحقاً، خلف نفس OpenAI-API (ADR-001).
**Consequences:** (+) تبديل المحرّك بلا تغيير الطبقات العليا. (−) فروق أداء/ميزات بين المحرّكين تحتاج اختباراً عند الانتقال.

## ADR-005 — Docker Compose أولاً (لا Kubernetes الآن)
**Status:** مقبول
**Context:** المرحلة الأولى تحتاج بساطة تشغيل وإعادة إنتاج، لا توسّعاً ضخماً.
**Decision:** التنسيق عبر Docker Compose مع إعدادات خارجية (config-driven)؛ Kubernetes مسار لاحق لا الآن.
**Consequences:** (+) إعداد بسيط وقابل لإعادة الإنتاج. (−) لا autoscaling/HA؛ مقبول في هذه المرحلة (YAGNI).

## ADR-006 — البدء بموديل managed أولاً
**Status:** مُستبدَل بـ ADR-010 (قرار المالك: البدء بموديل محلي)
**Context:** "نفس الشكل، صناديق أكبر" — أبسط بداية قيمة هي بوّابة + واجهة قدّام موديل managed.
**Decision:** البدء بموديل managed عبر LiteLLM؛ self-host قرار يفرضه مبرّر حقيقي (خصوصية/حجم).
**Consequences:** (+) قيمة سريعة دون عبء GPU. (−) كلفة/خصوصية تعتمد على المزوّد حتى يُتّخذ قرار self-host.

## ADR-007 — لا Kubernetes / SSO / HA / autoscaling في المرحلة الأولى
**Status:** مقبول
**Context:** خطر الهندسة المفرطة والتحسين المبكّر يهدّد البساطة (YAGNI).
**Decision:** تأجيل Kubernetes وSSO وHA وautoscaling؛ لا تُضاف إلا بطلب حقيقي موثّق بـ ADR لاحق.
**Consequences:** (+) تركيز ووضوح ونطاق محكوم. (−) إعادة زيارة هذه البنود عند نضج الاستخدام (مخطّط له، ليس مفاجأة).

## ADR-008 — أدوات فرض الجودة (Quality Tooling)
**Status:** مقبول (P-00 محسوم بلجنة تقييم + مراجعة عدائية؛ يُنفَّذ كـ scaffolding قبل أوّل كود)
**Context:** اختيار formatter/linter/type-checker والعتبات يحدّد كيف يُكتب ويُفحَص كل كود لاحق — قرار معماري يُبرَّر بالتقييم لا بالشيوع. **النطاق:** كود `llm-platform/` (حالياً صفر `.py`)؛ سكربتات QEWN السابقة هي sandbox بحثي **غير مشمول**.
**Criteria:** مطابقة الكود الفعلي · حَتمية+إصلاح تلقائي (AI يكتب) · توحيد الأدوات (anti-bloat) · سرعة · قابلية فرض CI · دعم عتباتنا · عكوسية/قلّة lock-in · صحّة صيانة وانتشار (لا موضة) · إشارة عالية.
**Decision:** **Ruff** (format+lint+import-sort+complexity موحّد، إصدار مُثبَّت) + **Mypy** (وضع basic؛ رُجّح على Pyrefly/Pyright لأن مكسب السرعة وهمي على هذا الحجم، ونضج Pyrefly غير كافٍ لبوّابة حمراء، ورفض Node يُعمَّم) + **pytest** (نجاح 0-fail بوّابة؛ التغطية **إشارة لا بوّابة**) + **gitleaks** الآن (yamllint/hadolint/`docker compose config` بالانتشار عند ظهور نوع الملف). الفرض: **pre-commit hooks + CI backstop** بنفس الفحوص (مصدر حقيقة واحد). العتبات: `complexity≤10` (C901) · `statements≤50/دالة` (PLR0915) · `args≤6` (PLR0913) = **بوّابات Ruff مع override مبرّر inline (لا تجاوز صامت)**. أمّا **`طول الملف≤180` = إرشادي** (Ruff لا يملك قاعدة طول-ملف؛ نتجنّب أداة رابعة — anti-bloat)، يُراجَع بشرياً ويُضاف فحص رخيص فقط عند ظهور تضخّم. أخطاء الصحّة/الأمان (gitleaks/mypy/E,F/pytest) = **بوّابات صلبة**. **Pyright مرفوض** (Node يكسر vendor-neutrality).
**Consequences:** (+) toolchain أدنى متناسب مع glue صغير، حتمي وقابل للإصلاح الذاتي، أقصى عكوسية (config في `pyproject.toml`، Mypy صفر-Node)، بوّابات pass/fail بلا انحراف محلي↔CI. (−) لا فرض تغطية رقمي حتى يظهر منطق حرج معزول (ADR لاحق)؛ تثبيت إصدارات Ruff/Mypy إلزامي للحَتمية. مؤجَّل قابل لإعادة الفتح بـ ADR: Pyrefly/ty عند النضج، عتبة تغطية، yamllint/hadolint.

## ADR-009 — إبقاء وثائق الحوكمة منفصلة (لا دمج في GOVERNANCE.md)
**Status:** مقبول
**Context:** سؤال مفتوح (META-BLOAT): هل تُدمج CONSTITUTION + ARCHITECTURE_RULES + ERROR_AND_OBSERVABILITY_POLICY في ملف واحد لتقليل العدد؟
**Decision:** تبقى منفصلة. كل وثيقة مسؤولية واحدة، < 180 سطر (R-ARCH-05)، ومترابطة بروابط. الدمج لا يضيف قيمة ويضخّم ملفاً واحداً فوق الحدّ.
**Consequences:** (+) فصل اهتمامات وقابلية قراءة وصيانة. (−) عدّة ملفات بدل واحد — مقبول، وهو نمط التوثيق الاحترافي.

## ADR-010 — البدء بموديل محلي (Gemma 4) بدل managed
**Status:** مقبول (يستبدل ADR-006) — مبدأ الموديل المحلي أولاً سارٍ؛ اختيار Gemma المبدئي استُبدل لاحقاً ([ADR-028](DECISIONS.md))
**Context:** قرار المالك: البدء بموديل Gemma 4 المحلي (مُنزَّل ومُثبَت عمله) بدل managed — متاح، مجاني، خاص، بلا اعتماد/مفتاح خارجي. والمرونة محفوظة (التبديل سطر واحد).
**Decision:** الـ backend الابتدائي لـ P-01 = محرّك محلي (llama.cpp) يخدم Gemma 4 خلف البوّابة عبر العقد `/v1`. managed يبقى تبديلاً بسطر واحد متى لزم (vendor-neutrality محفوظة).
**Consequences:** (+) تشغيل end-to-end فوري بلا تكلفة/مفتاح + خصوصية كاملة. (−) جودة موديل صغير محدودة (مقبول لـ pilot، يُبدَّل لاحقاً)؛ وإضافة طبقة المحرّك للـ stack تتطلّب قرار تشغيل GPU (Docker-GPU مقابل native) — يُحسَم تالياً.

## ADR-011 — تشغيل محرّك Gemma 4 داخل Docker (GPU)
**Status:** مقبول
**Context:** قرار المالك بعد عرض المفترق (Docker-GPU مقابل native): تشغيل المحرّك داخل Docker مع GPU، لأجل النظافة وقابلية النقل (الـ stack كله محاوى).
**Decision:** تُضاف خدمة محرّك (llama.cpp server بصورة CUDA) تخدم Gemma 4 على GPU وتكشف العقد `/v1` داخلياً؛ البوّابة تشير إليها. يتطلّب **NVIDIA Container Toolkit داخل WSL2** (شرط مسبق).
**Consequences:** (+) stack موحّد ومحاوى وقابل للنقل للسحابة (نفس النمط). (−) إعداد GPU-in-Docker أعقد على ويندوز؛ **ويجب التأكد أن صورة llama.cpp المستخدمة تدعم معمارية `gemma4`** قبل الاعتماد — قد نحتاج صورة مبنية من الـ wheel المخصّص إن لم تدعمها الصورة العامة.

## ADR-012 — معمارية الذاكرة (Memory)
**Status:** مقبول — **متقاعد إلى `future/context-engine` ([ADR-025](DECISIONS.md))**
**Context:** طلب المالك ذاكرة "بأفضل وسيلة". مسح موسوعي ([research/MEMORY_LANDSCAPE.md](../research/MEMORY_LANDSCAPE.md)، 11 مساعد) + قيود (6GB مؤقّت/الهدف GPU أقوى، حياد الموديل والواجهة، العربية). آلية الهوية per-user **مُثبَتة end-to-end** (تجربة حيّة).
**Decision:** ذاكرة per-user **خلف البوّابة عبر LiteLLM hook** (حياد الموديل والواجهة). المحرّك: **Mem0 self-hosted** (وضع vector، بلا graph) — استخراج/dedup/scoping جاهز عبر عقد /v1. التخزين: **pgvector** على Postgres الموجود (schema منفصل عن litellm). التضمين: **Qwen3-Embedding-0.6B** (multilingual، مثبّت one-way-door + `embedding_model_version`). العزل: `X-OpenWebUI-User-Id` (عبر `ENABLE_FORWARD_USER_INFO_HEADERS` — مُثبَت) + RLS. **HITL**: تأكيد بشري قبل الحفظ (مبدئياً). حوكمة: عرض/تصحيح/حذف per-user. يبدأ بسيط (RAG top-k)، يصعّد بالقياس.
**Consequences:** (+) حياد كامل، إعادة استخدام Postgres، عزل per-user آمن مُثبَت، صيانة أقل (Mem0 جاهز)، قابل للتوسّع للهدف السحابي، قابل للتبديل (نرجع لـ "صفر-إطار" أو نرقّي لـ Zep بسهولة). (−) Mem0 خدمة خامسة → **يعدّل R-ARCH-31** (تُضاف `mem0` لقائمة الخدمات، مبرَّر هنا). استخراج Mem0 يستهلك LLM (مقبول على GPU الهدف؛ على اللاب يُخنَق async/ليلي). **ثابت أمني حرج:** البوّابة تبقى داخلية وإلا انتحال الهوية عبر الـ header. جودة الاستخراج العربي تحتاج تحقّقاً + HITL مبكراً.

## ADR-013 — تنفيذ ذاكرة المرحلة 1 = خدمة L1 مخصّصة (لا Mem0 بعد)
**Status:** مقبول (يُكمّل/يعدّل تنفيذ ADR-012 لـ Phase 1) — **متقاعد إلى `future/context-engine` ([ADR-025](DECISIONS.md))**
**Context:** ADR-012 اعتمد Mem0 كهدف. عند التنفيذ تبيّن: صورة litellm بلا pg driver (httpx فقط)، وأبسط L1 (ذاكرة صريحة HITL) لا تحتاج embeddings ولا Mem0. مبدأ "ابدأ بسيط" (§5).
**Decision:** المرحلة 1 = **خدمة `memory` مخصّصة صغيرة** (FastAPI + asyncpg، جدول `memory.user_memory` معزول per-user) يناديها LiteLLM hook (`memory_hook.py`) عبر httpx؛ ذاكرة **صريحة (HITL)** بلا embeddings/vector. Mem0/RAG/المتجهات (هدف ADR-012) **مؤجّلة لـ L2** عند الحاجة. نفس النمط المعماري (hook → خدمة → Postgres) → قابلة للاستبدال بـ Mem0 لاحقاً دون تغيير العقد.
**Consequences:** (+) أبسط، صفر embedding/VRAM إضافي، تحت سيطرتنا الكاملة، مُختبَرة end-to-end (خزّن/استرجع per-user). (−) نصون منطقاً يدوياً بسيطاً؛ لا استرجاع دلالي بعد. الترقية لـ Mem0/L2 تبقى مفتوحة.

## ADR-014 — تفعيل الرؤية (Vision) عبر mmproj في llama-server
**Status:** مقبول ✅ مُنفَّذ ومُتحقَّق حيّاً (2026-06-25 — الموديل أجاب "أزرق" على صورة اختبار عبر العقد) — **معلَّق مؤقتاً بعد ADR-028** (mmproj خاص بـ llama.cpp؛ لا موديل multimodal يتّسع على 6GB تحت vLLM — تعود الرؤية مع GPU أكبر بتبديل الموديل، بلا mmproj)
**Context:** Gemma 4 E2B يدعم الصور معماريّاً لكنه نُشر نصّياً (بلا mmproj). بحث موثّق ([VISION_SETUP](../research/VISION_SETUP.md)) أكّد الإعداد والمزالق.
**Decision:** تحميل `mmproj-F16.gguf` (من نفس مستودع الموديل) وإضافته لـ llama-server بـ `--mmproj` + `--no-mmproj-offload` (المُرمِّز على CPU لتوفير VRAM على 6GB) + `--image-max-tokens` منخفض + ctx معقول. تعريف الموديل بـ `supports_vision: True` في LiteLLM. الصور بصيغة OpenAI `image_url`/base64 عبر OWUI→LiteLLM→llama-server.
**Consequences:** (+) دعم صور end-to-end بنفس العقد. (−) VRAM أضيق على 6GB (ذروة ترميز الصورة = المجهول الأكبر، مخفّفة بـ CPU projector + سقف توكنات)؛ قضايا llama.cpp معروفة (تطابق عائلة mmproj، `gemma4uv`، هشاشة مسار OWUI→LiteLLM) → استخدم أحدث صورة + اختبر فعلياً. مؤقّت على اللاب؛ مريح على GPU السحابة.

## ADR-015 — bootstrap مخطط الذاكرة تلقائياً عند الإقلاع (تصحيح ثغرة DoD)
**Status:** مقبول — **متقاعد إلى `future/context-engine` ([ADR-025](DECISIONS.md))**
**Context:** تدقيق (2026-06-25) كشف أن خدمة `memory` تستعلم جدول `memory.user_memory` دون أن يُنشئه أيّ كود — كان يُنشأ **يدوياً** وقت الاختبار، فيفشل صامتاً على volume نظيف (الـ hook fail-open يخفيه). انتهاك معيار "تمّ" ([CONSTITUTION](CONSTITUTION.md) §3: "بلا خطوات يدوية خفيّة")، رغم وسم PROGRESS_MAP "شغّال end-to-end".
**Decision:** يُنفَّذ DDL idempotent (`CREATE SCHEMA/TABLE/INDEX IF NOT EXISTS`) داخل lifespan خدمة `memory` عند الإقلاع (لا عبر init.sql مُركَّب على postgres، لئلا يعتمد على ترتيب/حالة الـ volume). فشل الـ DDL = فشل إقلاع صاخب (لا يُبتلع).
**Consequences:** (+) الذاكرة تعمل على `docker compose up` نظيف بلا خطوة يدوية؛ تحت سيطرة الخدمة. **مُتحقَّق حيّاً:** إسقاط الـ schema ثم الإقلاع يعيد إنشاءه + سطر `SCHEMA_READY`. (−) الخدمة تملك صلاحية DDL على مخططها المعزول (مقبول).

**Status:** مُستبدَل بـ ADR-017 (بُني على افتراض خاطئ لنيّة المالك)

## ADR-019 — Context Engine (ذاكرة L2): Orchestrator + خط أنابيب حتمي + 3 مخازن
**Status:** مقبول — 2026-06-25 (يطوّر هدف [ADR-012](DECISIONS.md)، يبني على [ADR-013](DECISIONS.md)) — **متقاعد إلى `future/context-engine` ([ADR-025](DECISIONS.md))**
**Context:** طلب المالك ذاكرة قوية: تاريخ طويل (محادثات + ملفات + تفضيلات) يتجاوز نافذة الموديل، عبر تخزين خارجي + استرجاع ذكي لما يلزم فقط. دراسة موسوعية (Mem0/Zep+Graphiti/Letta/hybrid/أنماط) + ورشة تصميم 16 خبيراً + مراجعة عدائية → رجّحت حلاً مخصّصاً على stackنا (Mem0 لا يلخّص التاريخ الطويل؛ Zep يفرض قاعدة رسم؛ Letta يقلب المعمارية).
**Decision:** بناء **Context Engine** داخل خدمة `memory` (لا حاوية جديدة عدا embeddings صغيرة): نقطة دخول وحيدة **Memory Orchestrator** (جامع، بلا قرار-LLM، توجيه بالصلة + بوّابات رخيصة) + خط أنابيب حتمي **Retrieve→Normalize→Rank→Compose** + 3 مخازن (user/conversation/file) موحّدة بعقد **`MemoryItem`** + **فصل حجم الذاكرة عن نافذة الموديل** (Context Builder يلائم السياق لكل طلب). v1 نحيف (لا تلخيص/High-Low-Water/RLS-كامل/parent-child). القرارات المقفلة وخطة M0–M5 في [specs/CONTEXT_ENGINE_V1.md](specs/CONTEXT_ENGINE_V1.md). يُحدِّث هدف ADR-012 (Mem0) → حلّ مخصّص قابل لإدخال إطار لاحقاً خلف نفس الواجهة.
**Consequences:** (+) يلبّي الهدف ضمن قيودنا (anti-bloat، إعادة استخدام Postgres، حتمي على 6GB، قابل للتبديل، عربي، HITL)؛ المسار الحارّ بلا LLM؛ المعمارية تكبر مع موديل أكبر بلا إعادة بناء. (−) منطق نبنيه ونصونه؛ الفائدة المرئية محدودة على نافذة 4096 (مقبول — معماري أولاً)؛ التلخيص/RLS/الملفات-المتقدّمة مؤجّلة v2 (مُسجَّلة، RLS+virtual-keys إلزامية قبل أي فتح خارجي). ملاحظة حوكمة: `docs/specs/` يحوي مواصفات تفصيلية معفاة من حدّ 180 سطر (R-ARCH-05).

## ADR-020 — تبديل صورة Postgres إلى pgvector (خطوة صفر لـ ADR-019، يعدّل P-01)
**Status:** مقبول — 2026-06-25 — **متقاعد فعلياً إلى `future/context-engine` ([ADR-025](DECISIONS.md))، ثم مُفعَّل مجدّداً بـ [ADR-029](DECISIONS.md)** (pgvector صار مخزن متجهات OWUI الفعلي)
**Context:** الاسترجاع الدلالي يحتاج امتداد pgvector؛ صورة `postgres:16-alpine` الحالية لا تملكه و`CREATE EXTENSION vector` يفشل عليها. P-01 ثبّت digest الصورة (checkpoint v9).
**Decision:** تبديل الصورة إلى `pgvector/pgvector:pg16` (تثبيت **digest جديد**)، مع **checkpoint قبل/بعد**. الـ bootstrap ينفّذ `CREATE EXTENSION IF NOT EXISTS vector / pg_trgm / unaccent` ويفشل **بصوت** (CONFIG error) لا stack-trace عند تعذّره. لا DDL متجهات قبل هبوط هذا.
**Consequences:** (+) يمكّن المتجهات والبحث الهجين بإعادة استخدام Postgres (لا قاعدة جديدة). (−) يعدّل digest المُثبَّت في P-01 (مقبول، مُسجَّل هنا) ويفقد قاعدة alpine الأخفّ (مقبول). البيانات محفوظة (نفس الـ named volume `postgres-data`).

## ADR-021 — ميزانية حقن واعية بالنافذة + عدّ التوكنات = بايتات UTF-8 (يصحّح القرار المقفل #6)
**Status:** مقبول — 2026-06-26 (تدقيق شامل + مراجعة عدائية) — **متقاعد إلى `future/context-engine` ([ADR-025](DECISIONS.md))**
**Context:** القرار المقفل #6 ([specs/CONTEXT_ENGINE_V1.md](specs/CONTEXT_ENGINE_V1.md)) ألزم: قراءة `model_info.max_input_tokens` (fail-fast) + tokenizer **حقيقي** + `injected+reserved ≤ window`. كشف التدقيق: (أ) الـ hook يثبّت 1000 ويتجاهل النافذة؛ (ب) `litellm-config` لا يصرّح `max_input_tokens` → fail-fast يكسر **كل** طلب؛ (ج) fail-open ([ADR-012](DECISIONS.md)) يناقض fail-fast؛ (د) **مراجعة عدائية** بقياس حيّ (Gemma `/tokenize`): التقدير بالحروف `ceil(len/2.5)` **يُقلّل** العدّ للأرقام/IBAN/التشكيل (IBAN: 15<28؛ كتلة قيست 295≤300 بينما الحقيقي 547 ⇒ تجاوز نافذة). بينما **بايتات UTF-8 ≥ عدد توكنات المحتوى دائماً** (كل توكن محتوى ≥ بايت؛ توكنات القالب/BOS الخاصة يستوعبها المحجوز؛ مقيس على 12 عيّنة عدائية) = حدّ أعلى مُثبَت. tokenizer حقيقي يحسّن الحشو لا الأمان ويُدخل ربطاً بالمحرّك (R-ARCH-10) وكموناً (§5).
**Decision:** v1 = **نافذة من الإعداد** (`CTX_MODEL_WINDOW`) + **محجوز** (`CTX_RESERVED_TOKENS`)؛ الميزانية = `min(CTX_INJECTION_BUDGET, window − reserved)` في الـ hook (**fail-open**: budget≤0 → لا حقن + `INJECTION_BUDGET_NONPOSITIVE`)؛ **`count_tokens = len(utf-8 bytes)`** (محافظ مُثبَت) والتأكيد نقطة واحدة في `compose` (بما أن bytes ≥ real ⇒ `block_bytes ≤ budget` يضمن `real ≤ budget`). اختبار خاصية على عيّنات أرقام/IBAN مقيسة. **tokenizer دقيق (engine `/tokenize`) + model_info + fail-fast → مؤجَّلة v2** (يصحّح القرار المقفل #6).
**Consequences:** (+) أمان مُثبَت رياضياً وقياساً، config-driven، fail-open، صفر تبعية/شبكة، حتمي. (−) إفراط ~2–5× في العدّ → حشو أقل (مقبول v1؛ يُحَل بـ tokenizer دقيق v2)؛ تبديل الموديل يحدّث `CTX_MODEL_WINDOW`. **اكتُشف خطأ التقدير الأوّل بمراجعة عدائية (مساعد فحص)** — مُسجَّل للشفافية.

## ADR-022 — استثناء R-ARCH-10 ضيّق (خدمة داخلية → محرّك محلي مجاني عبر /v1) + إضافة `embeddings` لقوائم R-ARCH-31/R-ERR-16
**Status:** قرار التوجيه **مُستبدَل بـ [ADR-023](DECISIONS.md)** (قرار المالك: التوجيه عبر البوّابة، لا استثناء)؛ **تعديل قائمة الخدمات (R-ARCH-31/R-ERR-16) يبقى سارياً** — 2026-06-26
**Context:** خدمة `memory` تنادي محرّك `embeddings` مباشرةً (`http://embeddings:8080/v1`) متخطّيةً البوّابة (يخالف ظاهرياً R-ARCH-10/12). قياس حيّ: البوّابة تُعيد **نفس المتجه بايتياً** (dim=1024، فرق=0) لكنها تضيف **~15ms (+50%)** لكل نداء على المسار الحارّ (كتابة + **كل** استرجاع)، وتتطلّب virtual key يُولَّد يدوياً (يخالف DoD §3 "بلا خطوات يدوية") + سرّاً جديداً + اقتراناً بدورة حياة البوّابة (gateway down → تضمين معطّل). والمحرّك **محلي مجاني** (لا توكنات مفوترة، لا مفتاح مزوّد، لا حصّة) ⇒ حوكمة البوّابة (كلفة/إسناد/حصّة، [ADR-002](DECISIONS.md)) **بلا قيمة فعلية هنا**. وأيضاً: `embeddings` خدمة سادسة غير مُدرَجة في قائمة R-ARCH-31/R-ERR-16 (ADR-019 أضافها دون تعديل القاعدة، خلافاً لسابقة [ADR-012](DECISIONS.md)).
**Decision:** (1) يُسمح **حصراً** لخدمة backend داخلية ضمن `services/` بمناداة محرّك **محلي مجاني** مباشرةً عبر العقد `/v1` على الشبكة الداخلية، بكل الشروط مجتمعةً: المنادي داخلي (لا frontend/خارجي) · العقد `/v1` حرفياً (R-ARCH-13 سليم) · العنوان **config-driven** (`EMBEDDINGS_URL`؛ التبديل لبوّابة/managed = سطر) · المحرّك **غير مكشوف** (`internal`، بلا `ports:`، R-ARCH-24 سليم) · **صفر مرور مفوتر/مزوّد-managed**. (2) تُضاف `embeddings` لقائمتَي R-ARCH-31 وR-ERR-16؛ ويُحدَّث R-ARCH-10 بإشارة لهذا الاستثناء.
**Triggers للعودة لـ R-ARCH-10 (توجيه عبر البوّابة، إلزامي):** أوّل تضمين managed/مفوتر · أو مستهلك ثانٍ خارج `services/` · أو أي فتح خارجي (ضمن حزمة v2 الأمنية). يبقى `embed-default` في `litellm-config` كـ**مسار البوّابة الجاهز** لهذا التبديل (موثّق، ليس dead config).
**Consequences:** (+) مسار حارّ أسرع ~50%، صفر سرّ/خطوة يدوية، استثناء **ضيّق قابل للفحص** (5 شروط + triggers صريحة)، حياديّة التبديل محفوظة (config-driven، R-ARCH-45). (−) خرق ظاهري لـ"كل شيء عبر البوّابة" — مقبول ومُسيَّج؛ فرض الـ triggers يدويّ (مراجعة) حتى أتمتته.

## ADR-023 — توجيه التضمين عبر البوّابة بلا استثناء (يُلغي قرار التوجيه في ADR-022) — قرار المالك
**Status:** مقبول — 2026-06-26 (قرار المالك، يستبدل قرار التوجيه في [ADR-022](DECISIONS.md))
**Context:** اختار [ADR-022](DECISIONS.md) النداء المباشر `memory → embeddings` باستثناء R-ARCH-10 ضيّق (مبرَّر بالكمون ~15ms + مجانية المحرّك المحلي). **رفض المالك الاستثناء صراحةً:** المنصّة تُبنى **قابلة للتوسّع في أي لحظة وللأقصى**، فيجب أن يمرّ **كل** مرور الموديل عبر البوّابة **بلا ثقوب** (R-LAW-05/R-ARCH-10، [ADR-002](DECISIONS.md)) — ليبقى التبديل/الإسناد/الحصص/المراقبة مركزياً وموحّداً عند النمو (managed، مستهلكون آخرون، فتح خارجي). الكمون والمفتاح الافتراضي ثمن مقبول للاتساق المعماري طويل الأمد.
**Decision:** `memory` يطلب التضمين عبر **البوّابة** (`EMBEDDINGS_URL=http://litellm:4000/v1`، موديل `embed-default`) بـ **virtual key مخصّص** (`MEMORY_LITELLM_KEY` مُولَّد بـ `/key/generate`، لا master ولا مفتاح المحرّك). المتجه **متطابق بايتياً** (قياس حيّ، dim=1024) ⇒ **لا re-embedding**. **كسر دورة الاعتماد:** `memory` لا يعتمد على `litellm` (fail-soft يغطّي نافذة الإقلاع)؛ `litellm` يعتمد على `embeddings` (service_started). يُحذف استثناء R-ARCH-10. تعديل قائمة الخدمات (R-ARCH-31/R-ERR-16) من ADR-022 **يبقى سارياً**. `embed-default` يصبح **مساراً حيّاً** لا flip-path.
**Consequences:** (+) العقد الموحّد **بلا ثقوب** (كل مرور موديل عبر البوّابة) → جاهز للتوسّع/managed/الإسناد المركزي؛ التبديل سطر واحد (R-ARCH-45). (−) ~15ms/+50% لكل تضمين على المسار الحارّ (مقبول)؛ خطوة إعداد موثّقة: توليد `MEMORY_LITELLM_KEY` (كنمط `OPENWEBUI_LITELLM_KEY`)؛ نداء re-entrant (hook→memory→بوّابة) — **مُتحقَّق حيّاً** بلا deadlock (litellm async، 3.2s). **ملاحظة توسّع (صدق):** النمط re-entrant يحجز slot بوّابة أثناء انتظار تضمين متداخل ⇒ يخفض التزامن الفعلي ~للنصف؛ آمن لـ1–10 مستخدمين، **يُراقَب عند الحجم** (عدد workers/حدود اتصال litellm، حوض asyncpg=5، p99 للتضمين). تخفيف: `EMBED_TIMEOUT≈8s` (يسقط سريعاً للفظي بدل حجز worker)؛ عند الحجم الكبير تُرفع حدود البوّابة/الحوض.

## ADR-024 — `item_id` = `gen_random_uuid()` (UUIDv4) في v1؛ uuidv7 مؤجَّل (يصحّح القرار المقفل #3)
**Status:** مقبول — 2026-06-26 (تدقيق شامل) — **متقاعد إلى `future/context-engine` ([ADR-025](DECISIONS.md))**
**Context:** القرار المقفل #3 ([ADR-019](DECISIONS.md) + المواصفة) ينصّ على `item_id uuidv7` (مرتّب زمنياً). لكن **PostgreSQL 16 لا يملك `uuidv7` مدمجاً** (متاح PG18+ أو امتداد `pg_uuidv7`)، والتنفيذ يستخدم `gen_random_uuid()` (UUIDv4 عشوائي). الترتيب الزمني على المعرّف **غير مطلوب فعلياً**: عمود `created_at` يوفّره، و`item_id` يُستخدم معرّفاً ثابتاً فريداً (dedup/مرجع) لا للترتيب.
**Decision:** v1 = `gen_random_uuid()` (UUIDv4) — صفر امتداد/تبعية جديدة (§5). **uuidv7 مؤجَّل** حتى ترقية PG18 (مدمج) أو حاجة فعلية لترتيب-زمني على المعرّف (حينها `pg_uuidv7` أو عمود v2). يصحّح القرار المقفل #3.
**Consequences:** (+) يعمل على PG16 بلا امتداد إضافي؛ الترتيب الزمني مكفول بـ `created_at`. (−) `item_id` غير مرتّب زمنياً (مقبول — لا يُستخدم للترتيب). تُحدَّث المواصفة §4/§5 لتطابق.

## ADR-025 — اعتماد ميزات OWUI المدمجة (RAG + Memory) كطبقة بيانات أساسية؛ تقاعد محرّك السياق المخصّص إلى فرع — قرار المالك
**Status:** مقبول — 2026-06-26 (قرار المالك، يقسم المشروع إلى مسارين)
**Context:** بُني محرّك سياق مخصّص (خدمة `memory` FastAPI + خدمة `embeddings` Qwen3 + `memory_hook` في البوّابة) عبر M0→M4b: ذاكرة مستخدم دلالية، التقاط محادثة تلقائي عابر للجلسات، تضمين عبر البوّابة. **تحقّق تجريبي على صورة OWUI المثبّتة** أظهر أن OWUI **يملك أصلاً**: (1) RAG مستندات ناضجاً (Chroma، تقطيع 1000/100، top-k، استشهادات، استخراج متعدّد الصيغ)؛ (2) ميزة **Memory** per-user دلالية (`Settings > Personalization > Memory`، مجموعة `user-memory-{id}`، `ENABLE_MEMORIES=True`). إعادة بناء ذلك في محرّكنا = تضخّم (§5). قرّر المالك الاعتماد الكامل على OWUI كطبقة بيانات وحيدة، وأن يكمّل محرّكنا الثغرات **لاحقاً** كميزة مستقبلية، مع سهولة الفصل.
**Decision:** (1) **المسار الأساسي (master) يعتمد OWUI كلياً**: تُزال خدمتا `memory` و`embeddings`، و`memory_hook`، وموديل `embed-default`، وكود `services/memory/` واختباراته، ومتغيّرات `CTX_*`/`EMBED_*`/`MEMORY_LITELLM_KEY`. الستاك الأساسي = **open-webui + litellm + llamacpp + postgres** (4 خدمات). الذاكرة/الملفات عبر OWUI المدمج (`ENABLE_MEMORIES=true`). (2) **الحفظ:** المحرّك الكامل (M0–M4b عند bbd3527) **محفوظ على فرع `future/context-engine`** على GitHub كميزة تطوير مستقبلية (ترقيمه ADR الخاص بفرعه مستقل عن هذا الخطّ). الفصل سهل: OWUI = البيانات الفعّالة؛ المحرّك = فرع مستقبلي.
**الثغرات المعروفة (مُتحقَّقة) التي يتركها OWUI** (تُعالَج مستقبلياً عبر فرع المحرّك إن لزم): التقاط محادثة تلقائي + استرجاع عابر للجلسات (لا يملكه OWUI)؛ التقاط حقائق تلقائي (ذاكرة OWUI يدوية/بأداة الموديل فقط)؛ تضمين عبر البوّابة model-agnostic (OWUI يضمّن بـ all-MiniLM-384 محلّياً خارج البوّابة — استثناء حالي قابل للعكس بالإعداد لـ [ADR-023](DECISIONS.md))؛ استرجاع hybrid (OWUI dense فقط).
**Consequences:** (+) صفر صيانة/تضخّم لمحرّك مكرّر؛ ستاك أنحف؛ ميزات OWUI ناضجة فوراً. (+) المحرّك غير مفقود (محفوظ على الفرع). (−) نخسر مؤقتاً الالتقاط التلقائي + hybrid + تضمين-عبر-البوّابة (مقبول بقرار المالك)؛ تضمين OWUI خارج البوّابة استثناء موثّق لـ ADR-023. (−) docs/specs/CONTEXT_ENGINE_V1.md ووثائق المحرّك تُوسَم "متقاعدة إلى الفرع" لا تُحذف. R-003: مسجَّل هنا.

## ADR-026 — حوكمة قابلة للتنفيذ (فحص ثوابت في CI) + تقوية تسجيل OWUI + نسخ احتياطي/smoke (معالجة تقييم العين الجديدة)
**Status:** مقبول — 2026-06-29
**Anti-Bloat (§5):** **مقبول.** الإضافة الوحيدة سكربت CI صغير (`.github/scripts/check_invariants.py`، stdlib + pyyaml) **يجسّد قواعد قائمة** (R-ARCH-31/24، R-LAW-06) بدل فحصها بالعين — **يقلّل المخاطرة لا يزيد السطح**، ولا طبقة/خدمة تشغيل جديدة. تقوية `ENABLE_SIGNUP` تنفيذ لقاعدة أمنية قائمة لا ميزة جديدة. (أوّل ADR يستعمل حقل §5 الصريح.)
**Context:** تقييم "عين جديدة" (4 مراجعين مستقلّين، 7/10) كشف أن **معظم الثوابت الحاملة تُفحَص بشرياً لا آلياً**، وأن ادّعاءات التشغيل الحيّ (دورة الدردشة، تتبّع `request_id`) **مُثبَتة ذاتياً بلا دليل آلي**، ولا قصّة **نسخ احتياطي** لـ `openwebui-data` (حيث صارت كل قيمة المستخدم بعد ADR-025)، وأن تسجيل OWUI متروك للافتراضي، وبقايا (مجلّدات فارغة + سرّ يتيم في `.env`).
**Decision:** (1) **فحص ثوابت آليّ في CI** (`check_invariants.py` في وظيفة build): أسماء الخدمات ⊆ القائمة (R-ARCH-31)، `open-webui` وحده يكشف منفذاً (R-ARCH-24)، الربط على 127.0.0.1 افتراضياً (R-LAW-06). (2) **e2e للدردشة + request_id يبقى يدوياً** (يحتاج GPU، غير متاح على runners) — سكربت smoke موثّق في [RUNBOOK](RUNBOOK.md). (3) **تقوية:** `ENABLE_SIGNUP=false` صريحاً في compose. (4) **نسخ احتياطي/استعادة** موثّق لـ `openwebui-data`/`postgres-data` في RUNBOOK (+ تحذير `LITELLM_SALT_KEY`). (5) تنظيف محلّي: حذف مجلّدات `services/`/`tests/` الفارغة وإزالة `MEMORY_LITELLM_KEY`/`CTX_*`/`EMBED_*` اليتيمة من `.env`. (6) ملاحظة مصدر الموديل في README.
**Consequences:** (+) أكبر كومة "حوكمة نثرية" صارت قابلة للتنفيذ؛ يُكسر الـ build عند أي خرق للكشف/التسمية. (+) سدّ فجوة النسخ الاحتياطي وأمان التسجيل قبل أي تعريض. (+) دليل smoke متكرّر للمسار الحيّ. (−) عودة بايثون بسيطة كـ**أداة CI** فقط (لا كود تطبيقي) — تعود mypy/pytest فقط متى عاد كود تطبيقي. (−) e2e للدردشة يبقى يدوياً حتى يتوفّر runner بـ GPU (أو mock-engine في CI، مؤجَّل §5). R-003: مسجَّل هنا.

## ADR-027 — llama-swap: موديلان محلّيان قابلان للاختيار على GPU واحد (تجربة موديل أكبر قبل Gemini)
**Status:** مقبول — 2026-06-29 (تجربة، قرار المالك) — **مُستبدَل بـ ADR-028** (انتهت التجربة؛ المحرّك صار vLLM)
**Anti-Bloat (§5):** **مقبول.** الحاجة صريحة (المالك يريد **موديلين قابلين للاختيار** لمقارنة الجودة قبل قرار Gemini). **6GB لا تتّسع للاثنين معاً** (E2B 3.3GB + E4B 4.2GB) → التبديل عند الطلب **ضرورة لا ترف**. llama-swap **أصغر حلّ قياسي**: وكيل واحد، **اسم الخدمة يبقى `llamacpp`** (لا خدمة/طبقة جديدة، لا تعديل لقائمة R-ARCH-31، فحص الثوابت أخضر). البديل (خدمة محرّك ثانية) يكسر R-ARCH-31 + يتطلّب VRAM غير متاح. تجربة **قابلة للعكس** (إرجاع صورة llama.cpp).
**Context:** Gemma 4 E2B صغير (عنق زجاجة للأدوات/الجودة، تقييم العين الجديدة). لتقدير هل موديل محلّي أكبر يكفي قبل القفز لـ Gemini السحابي (وما يرافقه من خصوصية)، نريد **Gemma 4 4B (E4B)** قابلاً للاختيار بجانب E2B على نفس البطاقة.
**Decision:** تُستبدَل صورة خدمة `llamacpp` بـ **llama-swap** (`ghcr.io/mostlygeek/llama-swap:unified-cuda`، يُحزّم llama-server CUDA) + إعداد `config/llama-swap/llama-swap.yaml` بموديلين: `gemma-4-e2b` (متعدّد الوسائط) و`gemma-4-e4b` (نصّي حالياً ليتّسع 6GB). llama-swap **يحمّل واحداً في الـ VRAM** ويبدّل بحقل `model`. يُضاف **"Gemma 4 4B"** في `litellm-config.yaml` (نفس نقطة المحرّك). مفتاح gateway→engine يُسقَط (المحرّك داخلي فقط — R-ARCH-24). الصورة تُثبَّت بـ digest.
**Consequences:** (+) موديلان قابلان للاختيار في OWUI على 6GB؛ مقارنة جودة مباشرة؛ يُثبت model-agnostic عملياً. (+) اسم الخدمة محفوظ → الحوكمة الآلية سليمة. (−) **كمون أوّل طلب** لموديل (تحميل/تبديل ثوانٍ). (−) E4B **نصّي حالياً** (الرؤية تحتاج ctx مخفّضاً ليتّسع — مؤجَّلة)؛ الرؤية تبقى على E2B. (−) `.env` متغيّرات `MODEL_FILE`/`MMPROJ_FILE`/`CTX_SIZE` لم تعد تُستخدم (الإعداد في llama-swap.yaml). تجربة قابلة للعكس. R-003: مسجَّل هنا.

## ADR-028 — التحوّل إلى vLLM محرّكاً وحيداً + تبديل موديل الاختبار إلى Qwen3-4B-AWQ (يستبدل ADR-027) — قرار المالك
**Status:** مقبول — 2026-07-02 (قرار المالك بعد دراسة موثّقة: 3 وكلاء بحث + 4 تحقّقات عدائية على مصادر أولية)
**Anti-Bloat (§5):** **مقبول.** لا خدمة/طبقة جديدة — استبدال صورة المحرّك (كنمط ADR-027) مع إعادة تسميته الصادقة (`llamacpp`→`vllm`، تعديل قائمة R-ARCH-31/R-ERR-16 وفحص الثوابت). الإضافات: ملف `config/vllm/vllm-config.yaml` **يحلّ محلّ** `llama-swap.yaml` (صفر صافي)، وvolumeان (كاش أوزان/ترجمة، قابلان لإعادة الإنشاء). القرار **قابل للعكس** (tag ‏`llamacpp-final` على آخر حالة llama.cpp + git history).
**Context:** مبدأ المالك: الموديل وGPU وحتى محلي-مقابل-API كلها تفاصيل اختبار — المنصّة تُبنى للتبديل بأقل مجهود، وvLLM هو محرّك الهدف السحابي أصلاً (ADR-004). الدراسة أثبتت: (أ) vLLM ناضج لبيئتنا (v0.24.0، digest مُتحقَّق، ملف config خارجي، `/health` بلا مصادقة، WSL2+بطاقات مستهلكين مؤكَّد)؛ (ب) **Gemma 4 تحت vLLM على 6GB مدحوض عدائياً من جهتين مستقلتين**: أصغر checkpoint قابل للخدمة = 8.3GB أوزاناً (vLLM يكمّم Linear فقط؛ PLE/embeddings تبقى bf16، والوصفة الرسمية تشترط 24GB+)، وGGUF الموجودة مرفوضة (`GGUF model with architecture gemma4 is not supported yet`)، وعلّة أداء مفتوحة على Ada (vllm#38887: ‏~9 tok/s على 4090؛ إصلاحها #38891 غير مدموج)؛ (ج) Qwen3-4B-AWQ (رسمي، غير مقفل، ~2.5GB، عربي ضمن 119 لغة، معمارية مدعومة أولى الدرجات بلا علّة الأداء) يتّسع على 6GB بسياق 8192.
**Decision:** (1) خدمة المحرّك تصبح **`vllm`** (صورة `vllm/vllm-openai:v0.24.0` بـ digest؛ تُحدَّث قائمتا R-ARCH-31/R-ERR-16 و`check_invariants.py`). (2) إعداد المحرّك في **`config/vllm/vllm-config.yaml`** (موديل، `served-model-name`، ‏`gpu-memory-utilization=0.75` لـ 6GB مشتركة مع العرض، `max-model-len=8192`، ‏`kv-cache-dtype=fp8`) — تبديل الموديل = تعديل سطرين فيه؛ ترقية GPU = رفع قيمتين فيه؛ **بلا تنزيل يدوي** (vLLM يسحب من HF تلقائياً إلى volume). (3) موديل الاختبار = **`Qwen/Qwen3-4B-AWQ`** باسم معروض "Qwen3 4B" (تسمية صادقة — ADR-017). (4) البوّابة عبر بادئة **`hosted_vllm/`** (مزوّد LiteLLM المخصّص لـ vLLM) و**يُزال `max_tokens: 2048` الافتراضي** (vLLM يرفض بـ 400 بدل القصّ عند تجاوز النافذة؛ غيابه = ملء المتبقّي). (5) مصادقة داخلية متناظرة عبر `VLLM_API_KEY` (بدل `LLAMACPP_API_KEY` غير المستهلَك). (6) **بلا `--reasoning-parser`** مبدئياً (علّة عرض مفتوحة open-webui#24697؛ وسوم think تصل inline وOWUI يطويها). (7) تُحذف `config/llama-swap/` وتُنظَّف متغيّرات GGUF اليتيمة من `.env.example`. (8) **تُعدَّل R-ARCH-14/R-ARCH-45 وقائمة تحقّق المراجعة** لتمييز مستويين: تبديل مزوّد/وجهة خلف البوّابة (config فقط) مقابل استبدال المحرّك نفسه (compose + config المحرّك + ADR) — وإلا كان هذا الـ PR يخالف نصّ R-ARCH-45 القديم حرفياً.
**Consequences:** (+) المحرّك = نسخة الهدف السحابي نفسها ("نفس الشكل، صناديق أكبر" حرفياً): ترقية GPU/موديل أكبر = تعديل قيم config فقط؛ managed = سطر في litellm-config (R-ARCH-45 كما هو). (+) تبديل موديل بلا خطوات يدوية (معرّف HF). (+) رصد أفضل (`/metrics` Prometheus) + continuous batching + prefix caching. (−) **الرؤية معلّقة مؤقتاً** (لا multimodal يتّسع على 6GB تحت vLLM؛ تعود مع GPU أكبر بتبديل الموديل — بلا mmproj). (−) موديل واحد مقيم يحجز VRAM دائماً (لا تبديل عند الطلب — نهاية تجربة ADR-027). (−) إقلاع بارد دقائق (torch.compile؛ مخفَّف بـ volume الكاش وstart_period). (−) صورة ~10.6GB. (−) `models-gemma4/` (~7.4GB GGUF) لم يعد مستخدماً — حذفه قرار مالك منفصل. علل upstream موثّقة تُراجَع عند الترقية: vllm#38887 (أداء Gemma على Ada)، open-webui#24697 (عرض reasoning)، BerriAI#25389 (usage في البثّ). R-003: مسجَّل هنا.

## ADR-029 — PostgreSQL + pgvector طبقةَ التخزين الدائمة؛ نقل OWUI من SQLite/Chroma إليها (نفس الخدمة، قاعدة/دور معزولان) — قرار المالك
**Status:** مقبول — 2026-07-02 (قرار المالك — **قرار أساسي دائم**) — **قرار الطوبولوجيا (نسخة مشتركة) مُستبدَل بـ [ADR-030](DECISIONS.md)**؛ يبقى سارياً: المحرّك الدائم PG+pgvector + least-privilege + قابلية تبديل الموقع
**Anti-Bloat (§5):** **مقبول.** **لا خدمة جديدة** — نعيد استخدام خدمة `postgres` (صورة pgvector) القائمة (R-ARCH-31 يبقى 4 خدمات، فحص الثوابت أخضر). يوحّد التخزين (يُلغي محرّكَي SQLite+Chroma المدمجين لصالح قاعدة واحدة قابلة للنسخ/الاستعلام/البناء فوقها)، **ويفعّل pgvector أخيراً** (كان بلا استخدام للمتجهات منذ ADR-020)، ويؤسّس ركيزة طبقة الـ Data Asset المستقبلية. الإضافة الوحيدة: سكربت `init` صغير + قاعدة/دور معزولان. قابلية العكس مفصّلة أدناه.
**Context:** OWUI كان يخزّن على **SQLite** (ميتاداتا) + **Chroma** (متجهات) داخل `openwebui-data` — صندوق ملفّي مغلق، صعب النسخ/الاستعلام/البناء فوقه. المالك يبني منصّة بيانات مؤسسية، والاتجاه (نموذج Data Asset فوق OWUI) يحتاج **قاعدة حقيقية نملكها**. عندنا أصلاً `postgres`+pgvector شغّال (حالة litellm) بقدرة متجهات فاضية — فالبنية التحتية جاهزة.
**Decision:** (1) **PostgreSQL + pgvector = طبقة التخزين الدائمة للمنصّة** — قرار أساسي: كل تخزين تملكه المنصّة عليها، لا SQLite/Chroma/محرّك ملفّي. (2) OWUI يخزّن على postgres: `DATABASE_URL` (ميتاداتا) + `VECTOR_DB=pgvector` + `PGVECTOR_DB_URL` (متجهات) → قاعدة **`openwebui`** داخل **نفس خدمة postgres** (صفر خدمة جديدة). (3) **least-privilege (قرار المالك — "لا نبني على أساس غلط")**: الـ superuser (`postgres`) **للإدارة فقط ولا يتصل به أي تطبيق**؛ كل تطبيق بدور عادي يملك قاعدته فقط (`litellm`→litellm، `openwebui`→openwebui) + **`REVOKE CONNECT ... FROM PUBLIC`** على القاعدتين (عزل CONNECT صلب بالاتجاهين، مُثبَت باختبار سلبي حيّ). هذا **شرط مسبق لأي RLS مستقبلي** (superuser/BYPASSRLS يتجاوز RLS — يزرع "role split" المطلوب في SECURITY.md). **حدّ صادق:** حساب الإدارة الفائق يظلّ قادراً على قراءة كل شيء (طبيعة أي قاعدة) — الضمانة أنه **ليس في مسار أي تطبيق**، وسرّه منفصل. (4) تهيئة الأدوار/القواعد/العزل/الامتداد عبر `config/postgres/init/10-app-roles.sh` (تلقائي على volume نظيف — أُثبت حيّاً؛ على القائم: تنفيذ السكربت نفسه يدوياً — RUNBOOK)، مع حارس CRLF (`.gitattributes`: ‏`*.sh eol=lf` — CRLF يكسر initdb، مُثبَت). (5) **بداية نظيفة** — بيانات SQLite/Chroma الاختبارية مركونة (غير مُتلِف)؛ إعادة تهيئة postgres أفقدت مفاتيح litellm الاختبارية → أعيد توليد virtual key (خطوة RUNBOOK الموثّقة).
**قابلية التبديل (موثّقة صراحةً — تجسيد حقل "كلفة العكس" §5):**
- **مكان تشغيل Postgres قابل للتبديل عبر الرابط فقط** (config-driven / 12-factor): محلي مُحاوى الآن ↔ **Postgres خارجي/مُدار** (RDS · Azure Database · Cloud SQL · Supabase) عند الانتقال لسيرفر — تغيير `host` في `DATABASE_URL`/`PGVECTOR_DB_URL` (المُدار غالباً يتطلّب إلحاق `?sslmode=require`)، **بلا تغيير schema/تطبيق/إعادة فهرسة**. محفّزات: الانتقال لسيرفر/سحابة · الحاجة لنسخ مُدارة/HA/replicas.
- **طوبولوجيا القاعدة قابلة للتبديل**: مشتركة (الآن) ↔ خدمة/نسخة منفصلة — عبر `pg_dump/restore` + تغيير الرابط. محفّزات: تزاحم موارد · عزل/امتثال · توسّع مستقل.
- **الثابت الدائم = المحرّك (PostgreSQL + pgvector)**؛ المتغيّر = أين/كيف يعمل. "نفس الشكل، صناديق أكبر".
**Consequences:** (+) قاعدة حقيقية واحدة قابلة للنسخ/الاستعلام/البناء فوقها (ركيزة Data Asset)؛ pgvector صار مُستخدَماً فعلاً؛ صفر خدمة جديدة؛ عزل بقاعدة/دور؛ **جاهز للانتقال لسيرفر خارجي بتغيير رابط**. **مُتحقَّق حيّاً (2026-07-02):** OWUI أنشأ 43 جدولاً في قاعدة `openwebui` (منها `access_grant`) + جدول `document_chunk.vector` (pgvector) بلا أخطاء، والخدمات الأربع healthy. (−) OWUI صار يعتمد على postgres (`depends_on: healthy`)؛ **نسخ OWUI الاحتياطي انتقل من الـ volume إلى `pg_dump`** (حُدِّث RUNBOOK؛ ملفّات الرفع-blobs تبقى على `openwebui-data`)؛ بيانات SQLite القديمة مركونة (تُحذف لاحقاً). ملاحظة تشغيل: على القاعدة النظيفة **أوّل مستخدم يُنشأ عبر الواجهة يصير الأدمن** (bootstrap رغم `ENABLE_SIGNUP=false`). لا يُلغي ADR-020 بل يُفعّله؛ يكمّل ADR-025 (OWUI طبقة البيانات). R-003: مسجَّل هنا.

## ADR-030 — نسخة PostgreSQL مخصّصة لكل تطبيق (postgres-litellm + postgres-openwebui) بدل النسخة المشتركة — قرار المالك
**Status:** مقبول — 2026-07-02 (قرار المالك، يستبدل قرار الطوبولوجيا في [ADR-029](DECISIONS.md))
**Anti-Bloat (§5):** **مقبول مع تسمية الكلفة بصدق.** هذه إضافة خدمة (5 خدمات؛ تُحدَّث R-ARCH-31/R-ERR-16 وفحص الثوابت). المبرّر ليس حاجة تشغيلية آنية بل **مبدأ المالك الصريح**: الشكل المحلي يجب أن يطابق شكل الإنتاج من الآن ("نفس الشكل، صناديق أكبر" حرفياً) — في الإنتاج قاعدة البوّابة وقاعدة بيانات الشركة صندوقان منفصلان حتماً (دورتا حياة/نسخ/ترقية/توسّع مختلفة)، وبناء الأساس الصحيح الآن يلغي "تعديل الفكرة ثم التوثيق ثم إعادة العمل" لاحقاً. الكلفة المقبولة: حاويةُ postgres إضافية (~عشرات MB ذاكرة، صورة واحدة مشتركة مثبّتة بـ digest — لا صورة جديدة تُدار) + سرّا إدارة منفصلان. قابل للعكس (دمج = pg_dump + رابط).
**Context:** ‏ADR-029 اعتمد نسخة مشتركة بقاعدتين معزولتين (الأبسط لحظتها، والانقسام موثّق كمحفّز مستقبلي). رفض المالك الانتظار: المنصّة تُبنى لتصبح منصّة بيانات الشركة (بيانات HR/مالية حسّاسة في قاعدة OWUI — اتجاه Data Asset)، وفصل عتاد بيانات الشركة عن حالة البوّابة **قرار إنتاجي مؤكَّد** لا يجوز تأجيل شكله.
**Decision:** خدمتا postgres مخصّصتان: **`postgres-litellm`** (حالة البوّابة) و**`postgres-openwebui`** (بيانات OWUI: ميتاداتا + متجهات pgvector)، بنفس الصورة المثبّتة، وكلتاهما بنموذج least-privilege الكامل من ADR-029 (superuser `postgres` إداري لكل نسخة بسرّ منفصل + دور تطبيق عادي يملك قاعدته + `REVOKE CONNECT FROM PUBLIC`) عبر سكربتَي init لكل نسخة (`config/postgres/{litellm,openwebui}-init/`). ‏ADR-029 يبقى سارياً في كل شيء عدا الطوبولوجيا (المحرّك الدائم PG+pgvector، least-privilege، قابلية تبديل الموقع لخارجي/مُدار بالرابط).
**Consequences:** (+) **عزل بنيوي** (دور كل تطبيق غير موجود أصلاً على نسخة الآخر — مُثبَت باختبار سلبي حيّ) وعطب/صيانة/ترقية أي قاعدة لا يمسّ الأخرى؛ نسخ احتياطي ودورة حياة مستقلان؛ الانتقال للإنتاج = رفع كل صندوق لمكانه المُدار بلا إعادة تشكيل. (+) **مُتحقَّق حيّاً:** النسختان healthy، ‏litellm ‏74 جدولاً وOWUI ‏43 + vector 0.8.3 كلٌّ على نسخته، دخان 200. (−) +حاوية وسرّان؛ (−) أوامر الإدارة/النسخ تستهدف نسختين (RUNBOOK محدَّث). R-003: مسجَّل هنا.

## ADR-031 — طبقة رصد الأداء (Prometheus + Grafana خلف profile monitoring) + تصحيح ادّعاء رصد الأخطاء — قرار المالك (تجاوز §5 واعٍ)
**Status:** مقبول — 2026-07-09 (قرار المالك: جاهزية مستقبلية صريحة، على فرع `feat/observability`)
**Anti-Bloat (§5):** **مقبول بتجاوز واعٍ من المالك — مع تسمية الكلفة بصدق.** حارس §5 يرفض افتراضياً +2 خدمة رصد على 1–10 مستخدمين (لا مستهلك آنٍ للوحات)، وتوصية المهندس + 11 مساعداً كانت "الأخفّ الآن، أجّل الثقيل بمحفّز موثّق". **لكن المالك قرّر صراحةً** بناء النظام جاهزاً "كي لا نرتّق لاحقاً" (منصّة مستقرّة قابلة للتوسّع/الإضافة/الحذف بأقل مجهود) — وهذه هي **الحاجة الموثّقة** (§5 يتطلّب تسجيل الحكم لا منعه). **تخفيف الكلفة:** الخدمتان خلف `profiles: [monitoring]` (لا تقلعان في `up` الأساسي — تبقى 5 خدمات الافتراضي)، مثبّتتان بـ digest، الإعداد/اللوحات ككود (reproducible)، grafana على 127.0.0.1 فقط. **قابل للحذف بسهولة** (احذف الكتلة + profile + volumeين) — تجسيد حقل "كلفة العكس".
**Context:** تدقيق observability (3 مدقّقين مستقلّين + مراجعة Codex) أكّد: **النوع الأول** (تسجيل/كلفة عند البوّابة) صحيح ومناسب للمرحلة لكن **مبالغ في وصفه** (R-ERR-15/16/19 يدّعي انتشار request_id عبر كل الطبقات — أُثبت فقط بخدمة `memory` المتقاعدة، ADR-025)؛ و**النوع الثاني** (مقاييس أداء: TTFT، امتلاء KV، طول الطابور، tokens/s) **غير موجود** — vLLM يكشف `/metrics` (Prometheus) لكن لا يُكشط. مبدأ المالك: بناء الأساس صحيحاً الآن يلغي إعادة العمل.
**Decision:** (1) خدمتان خلف `profiles: [monitoring]`: **`prometheus`** (يكشط vLLM `/metrics` بلا مصادقة كل 15ث، احتفاظ 30 يوماً، داخلي فقط) و**`grafana`** (لوحات على `127.0.0.1:${GRAFANA_PORT:-3001}` فقط). (2) إعداد ككود: `config/prometheus/prometheus.yml` + `config/grafana/provisioning/` (datasource + لوحة **"vLLM Inference"**: running/waiting، KV%، TTFT p50/95/99، tokens/s، preemptions، e2e latency، prefix-cache hit%). (3) **litellm `/metrics` مُستبعَد** — محجوب (401، enterprise؛ مُتحقَّق حيّاً حتى بمفتاح master)؛ كلفة/إنفاق البوّابة queryable في `postgres-litellm` (SpendLogs). (4) **توسيع R-ARCH-24 (ADR-031):** `grafana` يُضاف لقائمة الكشف المحلي (127.0.0.1 فقط) بجانب `open-webui`؛ تُحدَّث `check_invariants.py` (ALLOWED=7، `PORT_ALLOWED={open-webui,grafana}` + فرض digest-pin)، بيئة CI (`GRAFANA_ADMIN_PASSWORD`)، و`.env.example`. (5) **النوع الأول صُحّح بنفس الدفعة:** تضييق R-ERR-15/16/19 (الانتشار عبر الطبقات مؤجَّل حتى أوّل adapter) + فرض redaction (`turn_off_message_logging`) + دوران سجلّات (json-file 10m×3، `x-logging` anchor) + نسب إنفاق per-user (`ENABLE_FORWARD_USER_INFO_HEADERS`) + `BLE001` في ruff (يرفض except أعمى).
**Consequences:** (+) رؤية أداء حقيقية (KV/طابور/TTFT/tokens-s) — تجعل مبدأ "لا تزِد العتاد إلا حين تشبع الآليات فعلاً" **قابلاً للتنفيذ** (يوجد مقياس تشبّع). **مُتحقَّق حيّاً (2026-07-09):** prometheus يكشط vLLM الحيّ (target up)، استعلام Grafana→Prometheus ناجح (status=success)، اللوحة (7 لوحات) + datasource مُحمّلان ككود، litellm أُزيل بنظافة، مقياس KV مصحَّح (`kv_cache_usage_perc`). (+) قابل للإطفاء/الحذف بعلَم profile. (−) +2 خدمة رصد (كلفة §5 مقبولة بقرار مالك) + volumeان + سرّ Grafana. (−) مقاييس vLLM تختفي عند التحوّل لـ managed API (طبقة المحرّك قابلة للاستبدال) — الاستثمار الدائم عند البوّابة/postgres. (−) grafana يكشف منفذاً محليّاً (ثاني منفذ بعد OWUI — موثّق في SECURITY). R-003: مسجَّل هنا.
