**Overall Assessment**

The core shape is sound for Phase 1: `open-webui -> litellm -> vllm -> model`, with separate Postgres instances for LiteLLM state and Open WebUI data. The repo is unusually well-governed for a small Compose stack, and the current files mostly match the stated architecture. I would not call it production-ready for sensitive HR/Finance data yet. The main gap is not layering; it is identity, tenant isolation, operational hardening, and recovery.

Verified read-only: `check_invariants.py` passed, `docker compose config -q` passed with dummy env, all Compose images are digest-pinned, and `config/env/.env`/`backups/` are git-ignored. I did not run the GPU/e2e stack.

**Must-Fix**

1. **No real department/tenant isolation exists yet.** Open WebUI is the effective data boundary, while the `openwebui` DB role owns the whole OWUI database: [compose/docker-compose.yml](C:/Users/Aliodeh/Desktop/QEWN/compose/docker-compose.yml:83), [openwebui init](C:/Users/Aliodeh/Desktop/QEWN/config/postgres/openwebui-init/10-app-role.sh:8). The docs correctly say RLS/per-user keys/header stripping are required before external exposure: [.github/SECURITY.md](C:/Users/Aliodeh/Desktop/QEWN/.github/SECURITY.md:14). For HR/Finance, app-layer RBAC alone is not enough.

2. **Gateway attribution is shared, not per user/team.** OWUI uses one `OPENWEBUI_LITELLM_KEY`: [compose/docker-compose.yml](C:/Users/Aliodeh/Desktop/QEWN/compose/docker-compose.yml:79), and the runbook generates one alias `open-webui`: [RUNBOOK.md](C:/Users/Aliodeh/Desktop/QEWN/docs/RUNBOOK.md:36). LiteLLM spend/rate limits will attribute all UI traffic to that key unless user identity is explicitly forwarded and trusted.

3. **Admin bootstrap is a known takeover window.** On a clean DB, the first UI account becomes admin despite `ENABLE_SIGNUP=false`: [RUNBOOK.md](C:/Users/Aliodeh/Desktop/QEWN/docs/RUNBOOK.md:15), [DECISIONS.md](C:/Users/Aliodeh/Desktop/QEWN/docs/DECISIONS.md:226). Before any shared deployment, pre-provision the admin or gate the first run behind localhost/SSO only.

4. **DB password rotation is broken by the init scripts.** The scripts only create roles if missing; they do not `ALTER ROLE ... PASSWORD` when `.env` changes: [litellm init](C:/Users/Aliodeh/Desktop/QEWN/config/postgres/litellm-init/10-app-role.sh:8), [openwebui init](C:/Users/Aliodeh/Desktop/QEWN/config/postgres/openwebui-init/10-app-role.sh:8). Rotation will silently leave DB credentials out of sync.

5. **Container hardening and supply-chain controls are incomplete.** Digest pinning is good: [compose/docker-compose.yml](C:/Users/Aliodeh/Desktop/QEWN/compose/docker-compose.yml:14), but there is no image CVE/SBOM/provenance scan in CI, and the security policy accepts vLLM running as root: [.github/SECURITY.md](C:/Users/Aliodeh/Desktop/QEWN/.github/SECURITY.md:10). Add scanning plus `cap_drop`, `security_opt: no-new-privileges`, non-root where possible, and documented exceptions.

**Should-Fix**

- `check_invariants.py` only rejects extra services; it does not fail if a required service is missing: [.github/scripts/check_invariants.py](C:/Users/Aliodeh/Desktop/QEWN/.github/scripts/check_invariants.py:26). It also does not enforce digest pinning or `.env`/backup non-tracking despite the governance docs requiring those checks.

- Readiness is weaker than the docs imply. LiteLLM only waits for `vllm` to be started, not healthy: [compose/docker-compose.yml](C:/Users/Aliodeh/Desktop/QEWN/compose/docker-compose.yml:49). Users can reach OWUI while model calls still fail during cold start.

- Observability is overclaimed. The policy wants request IDs across layers: [ERROR_AND_OBSERVABILITY_POLICY.md](C:/Users/Aliodeh/Desktop/QEWN/docs/ERROR_AND_OBSERVABILITY_POLICY.md:93), but the runbook only confirms LiteLLM-side evidence at DEBUG/spend tracking: [RUNBOOK.md](C:/Users/Aliodeh/Desktop/QEWN/docs/RUNBOOK.md:88). Either implement propagation/collection or narrow the claim.

- The network is named `internal` but is not Docker `internal: true`: [compose/docker-compose.yml](C:/Users/Aliodeh/Desktop/QEWN/compose/docker-compose.yml:141). That is acceptable for HF/model downloads, but production needs an explicit egress policy or proxy.

- Backups are manual commands, not a recovery system: [RUNBOOK.md](C:/Users/Aliodeh/Desktop/QEWN/docs/RUNBOOK.md:64). Sensitive data needs scheduled encrypted backups, retention, and restore drills.

- Security docs contradict the OWUI embedding exception. SECURITY says all model traffic goes through LiteLLM: [.github/SECURITY.md](C:/Users/Aliodeh/Desktop/QEWN/.github/SECURITY.md:8), while RUNBOOK documents OWUI embeddings outside the gateway: [RUNBOOK.md](C:/Users/Aliodeh/Desktop/QEWN/docs/RUNBOOK.md:61). **Prioritized Action List**

1. Block production data until SSO/OIDC, group/department mapping, controlled admin bootstrap, and per-user/team LiteLLM attribution are designed and tested.
2. Fix Postgres init scripts for password rotation and add placeholder-secret validation.
3. Strengthen CI invariants: exact service set, digest pinning, no tracked `.env`/backups, no placeholder secrets in runtime env examples, link checks.
4. Add image scanning/SBOM/provenance and a digest refresh process.
5. Automate encrypted backups and prove restore.
6. Resolve the “all model traffic through gateway” vs OWUI local embeddings exception.
7. Reduce stale governance surface, especially `PROJECT_BLUEPRINT.md`.

The platform foundation is clean and directionally correct. The production risk is that sensitive company data would arrive before identity, isolation, recovery, and hardening catch up.
